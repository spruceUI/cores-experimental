# Audit and reduction, October 2026

The audit covered `feat/optimization-level-profiles` at `ce03c6c` (17 commits ahead of
`origin/main` = `f1a5a3f`, none of them pushed). The reduction is the
`refactor/lean-pipeline` branch built on top of it.

## Findings

### What no longer worked

1. **The repository's own validation failed on every checkout.** The 28 GB
   `.local-e2e/` evidence store (store, runs, campaigns, source mirrors) existed
   on no host any more; only np2kai's 120 MB store survived on one build host. The 115
   core-set pins referenced 563 paths inside it, so `catalog-check` exited 2
   (`pinned package is not readable`) and so did every command that resolved a
   track group: `core-track-*`, `prepare-release-source-graph`, `plan-release`,
   `seal-release`. The GitHub release-candidate path could not run, and 571 of
   the 1,913 tests (about 30%) could not run anywhere.
2. **`build-core` silently dropped `--optimization-profile`.** It rebuilt its
   arguments without the field, so the profile check in `e2e` saw `None` and
   built the baseline. A test asserted the forwarded fields and locked the bug
   in. The new ad-hoc variant workflow called exactly this path, so a
   `debug-v1` run would have uploaded release bytes labelled debug.
3. **The ad-hoc variant workflow could build about 12 cores.** It resolved
   builds through track groups, and 89 of 99 track cells were `deferred`; the
   admitted cells were all `universal`, so `:a133p` built without `-mcpu` while
   being labelled a133p. Its "fail fast" inventory step exited 0 for deferred
   cores. Nothing tested or audited it.
4. **The last release-candidate run failed** (2026-08-06): 98 of 100 cores built,
   `km_parallel_n64_xtreme_amped_turbo`'s package did not match its plan, and
   the seal job was skipped. No candidate had been sealed since 2026-07-24.
5. **Nothing ran automatically.** No workflow had a push, pull-request or
   schedule trigger, so `catalog-check` and the tests never ran in CI.
6. **Housekeeping:** all three pinned actions were node20 releases that GitHub
   now force-runs on node24; the 100 per-core workflows downloaded archives into
   the repository, so every build record said `repository_dirty: true`.

### Why an optimization dimension was so hard to add

GCC uses the last `-O` on the command line, and a core's makefile appends its
own `-O2` after the environment's `CFLAGS`, so an injected `-O3` loses (measured:
351 of 351 np2kai compiles stayed at `-O2`). Getting around that inside the old
pipeline meant changing every MAKEFLAGS producer (six separate code paths) and
all 89 per-core log contracts, because each one hashed full compile lines and
would reject any new flag. Adding one build dimension was a roughly 100-file
change.

### Where the size came from

| area | lines | what it was for |
|---|---|---|
| per-core contracts (`contracts/`) | 26,900 | 89 log proofs: hash every compile line, pin marker sequences. Only 133 lines were recipe logic (fbneo, mame2003_plus, picodrive). |
| campaigns (`campaign/`) | 20,300 | authority stages, phase freezes, transitions; 13,800 lines unreachable from any command |
| track registry (`tracks.py` + commands) | 6,700 | main/nightly/edge × stable/test × chipset, compare-and-swap promotion, source-order bindings; about 12 cells ever admitted; 19 MB of registry snapshots |
| evidence, pins, records, release lifecycle | about 20,000 | content-addressed store, golden/pin/candidate records and their re-validation |
| dependency-injection plumbing | about 5,000 | 13 service classes, 278 facade names, about 3,300 `services['…']` lookups |
| tests | 101,900 | 1,913 tests; 30% bound to the lost store |

All of it served to generate 190 container build scripts that total 13,171
lines of shell. Because `catalog-check` and `e2e` transitively imported 78,000
lines of the provenance lifecycle, removing unused commands alone could have cut
at most about a third of the code.

## What changed

| | before (`ce03c6c`) | after |
|---|---|---|
| tracked files | 1,057 | 82 |
| build tooling (Python) | about 108,000 lines | 1,054 lines (`scripts/cores.py`, `scripts/corebuild/`) |
| tests | about 102,000 lines, 1,913 tests | 198 lines, 17 tests, run on every push |
| workflows | 104 files | 6 files, 333 lines |
| JSON schemas, pins, campaigns, track snapshots | 34 schemas, 236 pin files (26 MB) | none |

**Kept:** the catalog (now with every per-core quirk as an explicit field, see
[catalog.md](catalog.md)), the patches, the metadata files, the Dockerfiles and
toolchain inputs, the toolchain digests (`manifests/toolchains.json`), the
chipset flags (`manifests/boards.json`) and the smoke loader.

**Same build commands.** For 188 of the 190 core/arch pairs, the new generator
emits token-for-token the same build commands as the old pipeline once its
proof-only lines are removed. The differences are deliberate: cap32's
`MAKEFLAGS=--trace` (log output only) and three patches that only made compile
lines visible to the old log proofs (chailove and dosbox_pure echo patches, and
picodrive's offsets-recipe patch).

**Validation criteria**, as decided during the refactor:

- experiments (the *Build cores* and *Cross product* workflows): the build
  produced the core and the core loads and initializes under qemu;
- release freezes: usable, and two builds (the second on half the CPUs) are
  byte-identical; the freeze manifest is the only place hashes are pinned;
- CI: every core usable at its catalog commit, or at its `known_good` recipe,
  which is reported as a warning.

**Variant flags** are appended by compiler wrappers as the last arguments of
every compile and link, so they win over the makefile; the release build of the
`universal` board runs without wrappers.

## Validation on the build host

All runs used the pinned toolchain images on the build host (16 cores, four core builds
in parallel).

| run | builds | result |
|---|---|---|
| baseline (every core, `universal` + `release`) | 190 in 17 min | 189 produced their core; 187 of the 188 load-testable ones load and initialize (all but flycast2024's are usable; flycast2021 does not link) |
| byte check against the old recorded artifacts (one-off, refactor check only) | 188 | 185 identical; hatari differed through short-hash drift and reproduces exactly with `git_abbrev`; km_parallel_n64 armhf is not reproducible |
| variant sample (10 cores × a133p, a33 × `max`, `debug`) | 34 | the wrapper reached compiles in all 34; failures were km_parallel_n64 on NEON (fixed with its switch) and mame2003_plus at `-O0` |
| freeze sample (2048, np2kai, gambatte, flycast, built twice) | 8 pairs | all byte-identical; the freeze manifest checks against itself |
| cross product (every core × every board at `max`) | 568 in 56 min | 558 usable, libgametank built (not load-tested), 8 failed: only flycast2021 (link) and flycast2024 (`.info`) |

The cross product's artifacts were re-tested with the final load test: every one of
the 562 load-testable artifacts loads and initializes. Against the release builds,
`max` artifacts are 1.02× the size at the median (0.64 for gme, which is
unoptimized by default, up to 1.50 for ecwolf on armhf) and take about as long to
build (median 1.04×).

## Found while validating the reduction

- **Short hashes drift with upstream size.** 58 artifacts embed a commit prefix
  whose length git chooses from the repository's object count. For the 50
  libretro-super cores that clone full history at build time, that length grows
  as upstream grows; hatari's went from 8 to 9 characters between August and
  October, changing its bytes. `git_abbrev` now pins each of them at its current
  length (hatari at 8, which reproduces its recorded artifact exactly).
- **km_parallel_n64_xtreme_amped_turbo armhf is not reproducible.** Its rebuild
  differs from the recorded artifact, which matches why the last
  release-candidate run failed on that core. A freeze would reject it until the
  cause is found.
- **NEON flags break cores that gate NEON assembly in the makefile.** With
  `-mfpu=neon-vfpv4` the compiler defines `__ARM_NEON__`, libretro-common's audio
  converters and resampler then reference their NEON assembly, and cores that
  only compile those `.S` files under `HAVE_NEON=1` fail to link
  (km_parallel_n64 on a33/ssd202d). Such cores need their NEON switch set for
  NEON boards.
- **flycast2024** builds, but libretro-super has no `flycast2024_libretro.info`,
  so its build stops at the metadata step.
- **The load test needs a frontend that behaves like RetroArch.** A loader that
  declines every environment call crashes healthy cores (cap32, hatari, atari800
  and others need a system directory or an accepted pixel format), and cores
  such as tic80 and puae2021 rely on the frontend having `libpthread` and `libm`
  loaded. cap32 reads its core options during `retro_init` and crashed until the
  loader answered them with their defaults, as RetroArch does. The loader now
  answers the directory, pixel-format, log, path and core-option calls, sets no-op
  callbacks before init and links both libraries.
- **gme ships unoptimized.** Its makefile passes no `-O` at all, so the release
  build is `-O0`; `max` makes it a third smaller.
- **`-O3` must not replace `-Ofast`.** chimerasnes, neocd, parallel_n64 and
  pcsx_rearmed build with `-Ofast`; a later `-O3` would drop the fast-math it
  implies, so `max` skips those compiles (pcsx_rearmed's a33 `max` build is
  byte-identical to its release build).
- **pcsx_rearmed gets its NEON GPU from the board flags alone.** Its makefile
  probes the compiler, so on a33/ssd202d it builds `BUILTIN_GPU=neon` with NEON
  assembly, where the universal armhf build (what spruce ships) uses the software
  `peops` renderer.

## Decisions (2026-10-07)

- `h700` gets `-mcpu=cortex-a53` like `a133p` (the H700 is a quad Cortex-A53); the old
  registry had left it untuned because the device was never probed.
- NEON boards keep `-mfpu=neon-vfpv4`; cores whose makefiles gate NEON assembly get
  their switch in the catalog's `neon` field as each one is found (km_parallel_n64:
  `HAVE_NEON=1`).
- The branch stays local; nothing is pushed or merged yet.
- The cross product builds every board at `max` only. Debug is a per-core choice in the
  *Build cores* workflow; it is proven on np2kai: its a133p debug build carries DWARF
  whose producer string records `-mcpu=cortex-a53 … -g -O2 -O0` (the makefile's `-O2`,
  then the appended `-O0`), all 351 compiles went through the wrapper, and the core
  loads. mame2003_plus is one core that does not survive `-O0` (it then references
  `hardhea2_decrypt`, which an optimized build discards).

## Open items

- **flycast2021 never built.** Its 2021 CMake links `-lGLESv3`, which the focal
  arm64 sysroot does not have (GLES3 symbols live in `libGLESv2`). It was a
  pending compile candidate under the old pipeline too.
- **NEON switches.** km_parallel_n64 and uae4arm have theirs (`HAVE_NEON=1`); the
  benchmark-only flag candidates are listed in [flags.md](flags.md). Nothing has
  been measured on a device yet: the runs prove the builds load, not that they are
  faster.
- **km_parallel_n64 armhf is not reproducible**; a freeze will reject it until the
  cause is found.
- **The other session's FlycastSlim and standalone-build work** (uncommitted in
  the main checkout) predates this layout and will need rebasing onto it.
- **Nothing is pushed.** `origin/main` is still `f1a5a3f`; merging this branch and
  pushing it is a separate decision. The workflows only run once they are on the
  default branch.
